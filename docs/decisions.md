# 기술 선택과 미결 사항

## 쓰는 것

React + TypeScript + Vite, React Router, TanStack Query, Tailwind, pdf.js로 프론트를 만들고
Vercel에 올린다. 백엔드는 FastAPI, SQLAlchemy 2.x, Alembic, Pydantic v2를 쓰고
PostgreSQL 16에 pgvector를 올린다. 파일은 S3, LLM은 Gemini, 논문 검색은 Semantic Scholar.
PDF 파싱은 Docling. 배포는 EC2 한 대에 docker compose, 앞에 Nginx를 둔다.
Python 3.11 이상, Node 20.

## 왜 모노레포인가

API 스키마가 바뀌면 프론트도 같이 바뀐다. 레포가 둘이면 두 개의 PR을 짝지어 관리해야 하는데
팀 규모에서 그럴 이유가 없다. 한 PR에서 양쪽을 고치고 같이 리뷰하는 편이 낫다.
배포 대상이 다른 건 Vercel에서 Root Directory를 `frontend`로 지정하면 해결된다.

## 왜 Redis 없이 DB로 큐를 만드나

처음엔 Celery를 생각했는데 지금 작업량에 비해 과하다고 봤다.

분석은 "학생이 PDF를 올릴 때 한 번"이고 지연에 민감하지 않다. 폴링 주기가 몇 초여도
전체 분석이 몇 분 걸리니까 체감되지 않는다. 반면 Redis를 띄우면 EC2 메모리를 더
쓰는데, Docling이 이미 메모리를 많이 먹는 상황이라 부담이다.

DB에 두면 따라오는 이점도 있다. 잡 상태와 재시도 횟수, 실패 사유가 테이블에 그대로
남아서 관리자 화면에서 조회하고 다시 넣기가 쉽다. 브로커를 쓰면 어차피 상태 조회용
테이블을 따로 만들게 된다. 그리고 문서 등록과 잡 생성이 같은 트랜잭션에 묶인다.
문서는 저장됐는데 잡이 유실되는 경우가 없다.

동시 업로드가 많아져서 폴링 지연이 보이거나, 주기 작업이 늘어나면 그때 Celery로 옮긴다.
파이프라인 코드가 큐 구현과 분리돼 있어서 바꾸는 비용은 크지 않다.

## 왜 벡터 DB를 따로 안 두나

과목과 개념 임베딩이 많아야 수만 건이다. 그리고 검색 결과를 과목·페이지·질문 테이블과
조인해서 써야 하는 경우가 대부분이라 같은 DB에 있는 게 편하다.

**임베딩 차원은 1536으로 고정한다.** pgvector의 HNSW·IVFFlat 인덱스가 2000차원까지만
지원하기 때문이다. Gemini 임베딩 기본 출력은 이보다 커서 그대로 쓰면 컬럼은 만들어져도
인덱스를 못 만들고 전수 스캔이 된다. 요청할 때 출력 차원을 줄여서 받는다.

나중에 바꾸면 컬럼 타입 변경에 인덱스 재생성에 전체 재임베딩까지 해야 한다.
첫 마이그레이션 전에 확정하고 환경변수로 박아 둔다.

## 왜 업로드가 서버를 안 거치나

수십 MB짜리 PDF가 EC2를 통과하면 메모리와 대역폭을 쓰고 타임아웃도 신경 써야 한다.
브라우저가 S3로 직접 보내면 그 문제가 없다. 대신 서버가 파일을 못 보니까
업로드 완료 시점에 S3에 실제로 객체가 있는지 확인하는 단계가 필요하다.

## 왜 Docling인가

강의 슬라이드는 레이아웃이 복잡하고 표와 도식이 많다. pypdf 같은 걸로 텍스트만 뽑으면
질문을 원문 어디에서 출발했는지 연결할 수 없다. 근거를 원문 위치에 묶는 게 이 프로젝트의
핵심이라 구조 정보가 필요하다.

대가로 메모리와 CPU를 많이 쓴다. 이게 EC2 사양을 정하는 기준이 된다.

# 먼저 확인해야 할 것

## HTTPS 없으면 연동 자체가 안 된다

Vercel은 HTTPS로 서비스된다. 여기서 `http://`로 열린 EC2 API를 부르면 브라우저가
mixed content로 막는다. IP로 접속하는 상태에선 인증서도 못 받는다.

도메인을 하나 잡아서 EC2 탄력적 IP에 연결하고, Nginx + Let's Encrypt로 HTTPS를 붙여야 한다.
CORS 허용 목록에 Vercel 프리뷰 도메인까지 넣는 것도 잊지 말 것.

로컬에서 개발할 땐 둘 다 http라 안 걸린다. 프론트를 실제 API에 붙이는 날 터진다.

## EC2 사양을 실측 없이 정하지 말 것

Docling이 레이아웃 모델을 로드해서 메모리를 상당히 쓴다. API 서버랑 같은 작은
인스턴스에 올리면 분석 중에 API가 느려지거나 OOM으로 죽는다. 프리티어 t2.micro(1GB)로는
어려울 것으로 본다.

실제 강의 PDF 몇 개로 메모리와 소요 시간을 먼저 재고 사양을 정한다. 이 숫자가
비용 추정의 기준이 된다. 그때까지는 워커 동시성 1, 컨테이너 메모리 제한을 걸어
워커가 API까지 끌고 죽지 않게 한다.

## 사전 생성 호출 수를 세어 볼 것

"PDF당 한 번"이라고 쓰긴 했지만, 50장짜리를 페이지마다 개념 추출하고 질문 만들고
과목 연결하면 PDF 하나에 100회가 넘는다. 학생 30명이 과목당 10개씩 올리면 금방 커진다.

페이지를 묶어서 보내고, 개념 추출과 질문 생성을 한 호출로 합칠 수 있는지 본다.
동향은 과목 단위 캐시라 문서 수와 무관하게 유지된다. 사용자당 업로드 상한을 둘지는
아직 안 정했다.

## Semantic Scholar 키

키 없이 쓰면 공용 레이트리밋이 낮아서 사전 생성 중에 429가 몰린다. 미리 신청해 두는 게 낫다.
호출은 직렬로 하고 백오프를 건다. 429가 계속되면 그 과목 동향만 비우고 분석 전체를
실패시키지는 않는다.

# 아직 안 정한 것

**SSU MCP 연동 범위.** 기획 단계 다이어그램에 점선으로 들어가 있는데, 교내 시스템
연동은 권한 문제가 걸리고 외부 의존이 크다. 1차는 학생 직접 업로드와 공개된 교육과정
자료로 한정하고, 핵심 흐름이 돌아간 다음에 붙이는 게 맞다고 본다. 교육과정 수집도
크롤링보다 파일 업로드를 기본으로 두는 쪽을 제안한다.

**가입 방식.** 학번 기반으로 할지 이메일로 할지. JWT access 30분 + refresh 14일,
역할은 학생/관리자 둘로 가는 것까지는 정했다. 관리자 계정은 가입 경로로 못 만들게 하고
시드 스크립트로만 만든다.

**유효 슬라이드 제외 기준.** 표지는 당연히 빼는데 목차, 참고문헌, 실습 안내는 어떻게
할지 안 정했다. 질문 생성 구현 전까지 정해야 한다.

**단일 EC2.** API, 워커, DB가 한 호스트에 있어서 하나 죽으면 다 영향받는다.
학기 프로젝트 범위에선 감수할 만하다고 보는데, DB 볼륨은 분리하고 pg_dump 백업은 걸어야 한다.
발표 전에 백업에서 복구하는 걸 한 번 실제로 해 보는 게 좋겠다.

**평가 로깅.** 검증 계획에 질문 품질, 연결 정확도, 학습 행동 지표가 있다. 이건 나중에
붙이려면 데이터가 없어서 못 한다. 질문 노출·펼침·저장·수정, 관련 과목 클릭, 원래
페이지 복귀 여부를 해당 화면 만들 때 같이 넣어야 한다.

비교 실험 조건(교육과정 정보 사용 여부, 질문을 목록에 둘지 본문 옆에 둘지)도
설정 플래그로 빼 둔다. 나중에 코드를 고쳐 가며 실험하면 조건이 오염된다.
