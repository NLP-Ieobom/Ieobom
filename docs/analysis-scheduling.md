# PDF 추출과 질문 생성 처리 규칙

PDF 열람·메모는 업로드 완료 이후 사용할 수 있다. 추출과 질문 생성은 백그라운드에서 진행한다.
여러 사용자가 자료를 올려도 한 사용자가 처리 차례를 독점하지 않도록 사용자별로 순환한다.
현재 공부하는 PDF에는 질문 생성 차례를 더 자주 주되, 나머지 PDF도 계속 처리한다.

## 워커와 처리 단위

| 워커 | 실행 수 | 한 차례의 작업 | 사용자 안의 문서 선택 |
| --- | --- | --- | --- |
| 추출 | 1개 | PDF 한 개 전체 추출 | 실행 가능한 문서 중 접수순 |
| 질문 생성 | 1개 | PDF의 최대 3페이지 | 최근 열람 PDF 2차례, 나머지 PDF 1차례 |

각 워커는 준비된 작업이 있는 사용자 중 가장 오래 차례를 받지 못한 사용자를 고른다.
아직 차례를 받지 않은 사용자가 먼저이고, 같은 조건이면 계정 생성 시각과 사용자 ID 순서로 고른다.
처리할 작업이 없는 사용자는 건너뛴다. 사용자 한 명만 남으면 그 사용자의 작업을 계속 처리한다.

추출과 질문 생성의 차례는 별도로 기록한다. A의 질문을 만드는 동안 B의 PDF를 추출할 수 있다.
같은 사용자도 앞 PDF의 질문 생성과 다음 PDF의 추출을 병행할 수 있다.
다만 Docling은 한 번에 한 문서만 실행한다. 이전 워커가 남긴 Docling 컨테이너가 실행 중이면
새 추출을 시작하지 않는다. Docling의 제한은 CPU 1개, 메모리 4GiB다.

이는 시간 할당 방식이 아니다. 실행 중인 추출이나 외부 API 호출을 중단해서 다른 사용자로 바꾸지 않는다.
페이지 내용과 외부 API 응답 시간에 따라 한 차례가 걸리는 시간은 다를 수 있다.

## 추출 순서

추출 결과가 없고, 실행 대기 중이며, 재시도 가능 시각이 지난 문서가 대상이다.
사용자를 고른 뒤 그 사용자의 문서를 분석 잡 접수 시각 순으로 선택한다.

A가 PDF 세 개, B가 두 개를 올렸고 둘 다 대기 중이라면, A부터 선택된 경우 다음처럼 진행한다.

```text
A의 첫 PDF / B의 첫 PDF / A의 두 번째 PDF / B의 두 번째 PDF / A의 세 번째 PDF
```

PDF 하나를 추출하면 원문 JSON·전체 페이지 수·페이지 행을 저장하고 질문 생성 대기로 넘긴다.
먼저 만들어진 페이지 행은 재사용하므로 추출 전에 저장한 메모도 유지된다.
추출 워커는 해당 문서의 질문 생성 완료를 기다리지 않고 다음 사용자를 고른다.

## 질문 생성 순서

추출 결과가 저장됐고 실행 가능한 문서가 대상이다. 각 사용자에게 한 번에 최대 3페이지 묶음 하나를 배정한다.
묶음은 원래 PDF의 페이지 순서로 구성하고, 이미 저장된 페이지는 건너뛴다. 마지막 묶음이나
재개한 묶음은 3페이지보다 적을 수 있다. 표지 등 질문 생성 제외 페이지도 처리한 페이지에 포함한다.

우선 문서는 서버의 `user_document_progress.last_viewed_at`이 가장 최근인 PDF 한 개다.
뷰어에서 페이지가 표시되고 진도 저장 요청이 성공하면 현재 열어 둔 PDF가 이 대상이 된다.
브라우저에 저장된 ‘최근 공부한 페이지’ 목록 전체를 우선 대상으로 삼지는 않는다.
여러 기기나 탭에서 열면 서버에 기록된 마지막 열람 시각을 기준으로 한다.

사용자의 차례가 돌아오면 아래 규칙으로 문서를 선택한다.

1. 우선 문서에 두 차례를 배정한다.
2. 다음 차례는 나머지 문서 중 가장 오래 처리 차례를 받지 못한 문서에 배정한다.
3. 나머지 문서를 처리하면 우선 배정 횟수를 0으로 되돌리고 반복한다.

횟수는 성공한 묶음 수가 아니라 실제 작업을 배정한 횟수다. 실패한 호출도 차례를 사용한 것으로 센다.
우선 문서가 바뀌어도 횟수를 초기화하지 않으므로, 계속 다른 PDF를 열어도 나머지 문서의 차례는 유지된다.

우선 문서가 완료됐거나 아직 추출 전이거나 재시도 대기 중이면 나머지 문서를 순환한다.
열람 기록이 없어도 같은 방식으로 순환한다. 나머지 문서가 없으면 우선 문서를 계속 처리한다.
한 번도 처리하지 않은 문서는 먼저 선택하고, 같은 조건이면 접수 시각과 잡 ID로 순서를 정한다.

A의 우선 문서가 A2이고 나머지가 A1·A3일 때, A가 받는 차례만 보면 다음과 같다.

```text
A2의 3페이지 / A2의 다음 3페이지 / A1의 3페이지
A2의 다음 3페이지 / A2의 다음 3페이지 / A3의 3페이지
```

다른 사용자도 대기 중이면 위 차례 사이에 그 사용자의 묶음이 들어간다.
문서별 완료 순서는 보장하지 않는다. 분량이 적거나 오류가 없는 문서가 먼저 완료될 수 있다.

## 질문과 논문 공개

한 묶음의 질문 생성과 근거 검증이 끝나면 질문 행과 결과 JSON, 처리 페이지 수를 같은 트랜잭션으로
저장한다. 과목·논문 추천은 가능한 범위에서 함께 저장하되, 외부 검색이나 추천 선택이 실패해도
검증을 마친 질문 공개를 막지 않는다. 이때 해당 페이지는 `research_status=unavailable`이고 논문 목록은
비어 있을 수 있다. 연구 동향 기능이 꺼진 과목은 논문 검색을 생략한다.

이미 공개한 묶음은 다음 묶음의 실패와 무관하게 열람할 수 있다. 재개할 때 완료 페이지를 다시 만들지
않으므로 질문 ID와 저장 표시가 유지된다. 문서에서 발견한 연구 주제·검색어·논문 후보·검색 실패 쿨다운은
`document_learning.research_topics`에 누적한다. 다음 페이지 묶음은 Gemini가 새 질문을 이 목록의 기존
주제에 먼저 배정하며, 후보가 질문과 직접 관련되지 않을 때만 보충 검색어를 만든다. 같은 주제에는 최대
세 개의 검색어만 허용한다. 성공한 Semantic Scholar 원문 응답도 요약 전에 저장하므로 Gemini 요약이
실패해도 외부 검색을 반복하지 않는다.

검증을 통과한 질문 초안과 현재 묶음의 주제 배정은 `document_learning.pending_batch`에 내부 저장한다.
묶음을 공개하는 트랜잭션에서 임시 결과와 연속 실패 기록을 함께 지운다.
모든 페이지가 저장되면 문서의 잡을 완료 처리한다.

## 대기와 실패

정상적인 차례 교대도 `pending / queued`로 표시한다. 완료 페이지 수는 유지하고,
`error_code`, `error_message`, `next_retry_at`은 비워 둔다. 오류로 재시도하는 경우에만 오류 정보와
재시도 가능 시각을 반환한다. 해당 시각은 작업 시작 보장 시각이 아니라 대기열에 다시 참여할 수 있는 시각이다.

`attempt`는 최초 실행과 오류 후 재실행을 누적해서 센다. 정상적인 묶음 완료나 추출·질문 워커 사이
인계로는 증가하지 않는다. 수동 재시도도 이전 횟수를 지우지 않고 새 시도를 배정한다.

질문 생성의 일시 오류는 같은 묶음의 연속 실패 횟수에 따라 30초, 60초, 120초, 240초, 480초,
이후 최대 10분 간격으로 다시 배정한다. 기다리는 문서는 건너뛰고 다른 문서를 처리하며,
대기가 끝나면 기존 사용자 순환과 2:1 규칙에 다시 참여한다. 묶음 공개에 성공하면 연속 실패 횟수와
첫 실패 시각을 초기화하므로 앞 묶음의 오류가 다음 묶음의 재시도 기회를 줄이지 않는다.

같은 묶음의 첫 실패부터 1시간이 지나면 `failed / AI_RETRY_EXHAUSTED`로 일시 중단한다.
차례를 기다린 시간도 포함하며, 제한 시간이 지난 뒤에는 새 차례를 시작하지 않는다. 이미 실행 중인
묶음이 성공하면 저장할 수 있다. 수동 `/retry`는 제한 시간을 초기화하고 임시 결과와 완료한 페이지를
유지한 채 재개한다. 권한·요청 거절 등 재시도 불가능한 오류는 바로 중단한다.
추출 워커의 잠금 만료 회수는 기존 기본 한도 3회를 유지한다.

차례와 실행 잠금은 DB에 저장한다. 재시작해도 우선순위 횟수와 문서별 마지막 처리 시각이 유지된다.
워커 중단 시 잠금 회수와 수동 재시도 동작은 [실패와 복구](architecture.md#실패와-복구)를 따른다.
HTTP 상태와 필드 정의는 [분석 상태 API](api.md)에 있다.

## 배포와 확인

마이그레이션 `91c5a8e237df`가 사용자별 추출·질문 차례, 우선 배정 횟수, 문서별 질문 처리 시각을 추가한다.
기존 문서나 질문을 다시 생성하지 않는다. Compose의 `extractor`는 추출을, `worker`는 질문 생성을 맡는다.
컨테이너 이름은 각각 `ieobom-extractor`, `ieobom-worker`다.

마이그레이션 `6c30e7d14b92`는 미완료 묶음의 임시 결과와 연속 실패 횟수·첫 실패 시각을 추가한다.
이미 실패한 문서는 배포만으로 자동 재개하지 않으며 `/retry`로 다시 요청한다.

마이그레이션 `7d41c9e2a6b0`은 문서별 연구 주제와 재사용할 논문 후보를 추가한다. Semantic Scholar는
새 검색어마다 한 번만 호출한다. 429는 15분, 그 밖의 오류는 5분 동안 같은 검색어의 호출을 쉬며,
그동안에도 질문 분석은 계속 완료 처리한다.

배포 전에 EC2 디스크 공간을 확보한다. 실행 이미지·Docling 이미지·DB 볼륨·모델 캐시를 보존하면서
불필요한 빌드 캐시와 이전 배포 이미지를 구분해서 정리한다. Docker가 회수 가능하다고 표시한 이미지에도
현재 실행 중이지 않은 Docling 이미지가 포함될 수 있다.

배포 후에는 두 사용자에게 PDF를 여러 개 올려 추출 사용자 순환을 확인하고, 한 문서를 열어
질문 생성의 2:1 우선 배정을 확인한다. 메모는 추출 전에 저장하고 추출 후에도 유지되는지 확인한다.
논문 검색 실패 중 질문 공개, 주제 후보 재사용, 재시도 시 기존 질문 유지, Docling 실행 중 최대 메모리
사용량도 확인한다.
웹페이지 완료 알림과 푸시 알림은 이번 범위에 포함하지 않는다.
